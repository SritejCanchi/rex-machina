Rex Machina

Agent-generated game content, a boss that is itself an agent, and what it takes to put AI inside an engine and its editor.

Sritej Canchi · Capstone, Multi-Agent AI for Game Development (ELVTR, 2026) · Browser build, an Unreal Engine 5.5 port, and a Unity 6.6 port in progress

Play in the browser (2 min) Source on GitHub

Summary

  • Every line of game content is agent-generated. Five pipelines write 42 rows into engine DataTables, copied into the build with a checksum on both ends.
  • The boss is an agent that predicts the player's next tile and cuts it off instead of chasing, and only says what it actually measured.
  • $0.25 total model spend, $0 per play. Generation runs at authoring time, so the shipped game makes no model calls. Haiku 4.5 was chosen on a cost model, below.
  • Verified against the running game, not the spec: an adversarial QA agent runs about 3,000 checks per build and found 3 real bugs.
  • Ported to Unreal 5.5: Blueprint graphs generated as text, linted, self-tested, and packaged for Windows.
  • Next: Unity 6.6 with Unity AI. The same tables load unchanged, and the remaining art, voice and sound cost an estimated $6–11 in credits, once.

The game

A shelter dog walks nine days home to the family that gave her away, and finds a robot dog in her place. Six chase encounters lead to one boss fight. The design rule from the course: one agent, one wow.

The robot reads the player's last few moves, walks to the tile it predicts, and names what it measured, for example “Two of the last four moves cancelled out.” Repeat a trick and it stops working. Wait long enough and it forgets.

Would a bigger model pay for itself with fewer retries?

A pricier model is cheaper only if it needs proportionally fewer calls. The retry-line pipeline is the clean test, because its rule checks are plain code and cost nothing.

cheaper only if
  calls_big  <  calls_haiku
               × price_haiku / price_big

retry-line pipeline on Haiku: 23 calls
  6 first drafts + 17 rewrites
  floor: 6 calls, one draft per line
  the rule checks between drafts are free code

Sonnet 5.5, 2× the price
  break-even below 11.5 calls
  needs about two thirds fewer rewrites

Opus 5.5, 4× the price
  break-even below 5.75 calls
  under the 6-call floor, so it cannot win

Decision

At authoring time, the model choice is worth 74 cents. Cost does not decide it there. Rule checks, a style score and an adversarial QA pass already stand between the model and the build, so a larger model buys little.

At runtime, the same choice multiplies the cost of every play by 2 to 4, and the call is hidden behind a 600 ms turn animation, so speed matters too. The boss's job is narrow: read a small JSON of observed moves, pick a tile, say one line. That is a small-model task, so Haiku 4.5 is the default.

The model is one constant per pipeline, so changing it is a measured swap, not a rewrite. The one experiment worth running is whether Sonnet clears the retry rules on its first draft often enough to cross break-even.

Record and replay made every test run free. Each model call is recorded once and replayed from disk afterwards, which cut a style-pipeline test run from about $0.037 to $0 and lets anyone rebuild every output from a clean checkout with no API key.

Lessons for in-editor AI

1. Ground generation in the project

Retrieval ran over the game's own design document, split into 39 chunks, and every generated row records where it came from. The project in front of an editor is the best knowledge base a generator will ever get.

2. Emit what the engine already reads

The agents wrote DataTables, not prose. Every output is diffable, checksummed and testable, and the same 42 rows drive two engines with no hand edits. Engine-native output turns a model's answer into a reviewable asset.

3. Validate against the running game, not the document

One boss line passed retrieval grounding, a rule evaluator and a style evaluator, and still told a player who had run right nine times that it “favored left.” An agent that played the build caught it in seconds. A check that reads a document cannot see game state. Only a check that runs the game can. The fix holds a line back unless it is true, because silence beats a confident lie.

4. Compiling is not working

The Unreal port uses 18 Blueprint graphs generated as text. Four mistakes compiled clean and returned constants. A linter caught ten dropped wires before paste, and a self-test level that prints each function's values caught the rest. An agent that writes code or graphs needs an oracle that runs the result.

5. An agent cannot drive what it cannot see

Unreal has no Python API for building Blueprint graphs, so every graph went in through the clipboard. Editor windows screenshot as black frames, the headless Python runner logs to a file instead of the console, and a script path with a space is silently cut short. Each one made a failure look like success. In-editor agents need structured editor state and first-class actions, not pixels and paste.

6. Separate authoring cost from runtime cost

Pre-generating content made every play free. Generate at authoring time, where it is cheap and reviewable. Spend at runtime only where it earns its cost.

Unreal Engine 5.5 port

  • The same five DataTables drive the fight.
  • 18 Blueprint graphs generated as text by a Python generator, linted before paste, verified by a self-test level.
  • Packaged for Windows from a script: 27 minutes, 265 MB zipped. Three key presses advance exactly three rounds.
  • Audio imported and verified, seven cue families matched to the sound beds the pipeline wrote. Not yet wired into the graphs.

What's next: Unity 6.6 and Unity AI

The same data contract now opens in Unity 6.6 (6000.6.2f1) with Unity AI, on the trial plan. The five tables loaded without a single edit. A 33-line editor importer turns DT_NemesisReads.json into a ScriptableObject (24 rows), and the yard arena is built from DT_ArenaPhases, with exits and cover where the table puts them.

One question to the Assistant, checked against the data

The question: which reads fire if the player moves right six turns in a row? The Assistant opened the JSON and the design doc, then returned six rows. All six IDs, triggers and lines match the table exactly.

It also noticed the stored lines say “left” while the move was right, then assumed the game swaps in the observed direction at runtime. It does not. The shipped game holds that line back, a fix the QA agent forced (RM-001). Grounded in the files, guessing about the running game: lesson 3 again, and the gap an in-editor agent closes by reading play-mode state, not only source.

Friction worth reporting

  • A new project spent 8 minutes resolving packages before the editor opened.
  • MCP calls cannot trigger editor menu items (“user interactions are not supported”), so the importer had to be invoked by reflection.
  • The MCP link drops on every script recompile and returns once the domain reload finishes.
